# Contributing

## Getting it running

You do not need MetaTrader 5, a broker account, or a network connection. The
repository ships a synthetic dataset and everything runs against it.

```
python -m venv .venv
.venv/Scripts/python -m pip install -e ".[dev]"     # Linux/macOS: .venv/bin/python
.venv/Scripts/python -m pytest -q
.venv/Scripts/python run.py
```

CI runs the suite on Linux and Windows, on Python 3.10 and 3.12, with
`-m "not mt5"`. If your change passes locally without a terminal, it will pass
there.

## Before opening a pull request

```
python -m pytest -q          # the suite
python -m ruff check .       # lint
python -m mypy               # types, on core/
cd ui && npx tsc --noEmit && npm run build
```

## The rules that are not style preferences

This project's entire claim is that its numbers can be trusted. A few rules
protect that, and a change that breaks one of them is not a change worth
making faster.

**Results may not move silently.** `tests/golden/` pins a complete trade list
and every metric for two frozen runs. If your change alters any of them, the
test fails, and the fix is to declare it:

```
python -m scripts.update_golden --update-golden --note "why the numbers moved"
```

The note is mandatory and lands in `ENGINE_CHANGELOG.md`. Regenerating a
reference without one, or to make a red build green, defeats the only
mechanism here that catches an accidental change in behaviour.

**The simulator and the trader are one implementation.** Execution rules live
in `core/engine/execution.py`. The backtester drives that state machine over
a DataFrame; the live runner drives the same one bar by bar.
`tests/test_replay_equivalence.py` replays history through the runner and
demands trades identical to the backtest, to the timestamp and the price. Do
not add an execution rule to one side.

**Inputs that decide a result are pinned, not re-read.** `tick_value` moves
with an FX rate and brokers change swap rates without notice, so a run stores
the instrument spec it used, and so does a live diary. Comparing two records
that were handed different specs measures the specs. If you are adding
something that reads a spec at comparison time, it is almost certainly a bug -
see the note at the top of `core/live/compare.py`.

**The committed campaign is an artefact, not a scratch file.** `campaigns/`
holds the report the README's central claim rests on, with the manifest that
freezes the contracts it ran against. Re-running it overwrites that report, so
if you only want to check that it still reproduces, use the verifier - it
writes nothing unless asked:

```
python -m scripts.verify_campaign campaigns/02-deep-history-2020.yaml \
    --manifest campaigns/02-deep-history-2020.manifest.json \
    --report   campaigns/02-deep-history-2020.report.json
```

It needs the bars, which are not in the repository. If you do replace the
report, `campaigns/README.md` has to say what moved and why, the same way the
engine changelog does.

**Do not widen what can send an order.** The research half of the codebase
cannot trade. The live runner defaults to dry run and refuses a non-demo
account when told to send. Both of those are tested.

**A number without its uncertainty is not a result.** Metrics carry their
observation count and standard error, and a test without the power to say
anything says so instead of returning a figure. New metrics follow the same
rule.

## The synthetic fixture

`fixtures/data_cache/` is generated by `scripts/make_fixture.py` and is
committed so a clone has data. It is **invented** - a random walk with a
plausible spread, session week and volume profile. Nothing measured on it
describes a market, and it is labelled `synthetic_fixture` in the cache
provenance so that a run over it cannot be mistaken for one over real bars.

It is also load-bearing: the golden references are measured on it, and a test
regenerates it and diffs it against what is committed. If you change the
generator, that test fails and both must be regenerated together:

```
python -m scripts.make_fixture --clean
python -m scripts.update_golden --update-golden --target fixture --note "..."
```

## Style

Match the file you are editing. Comments explain *why*, not *what*, and the
existing density is the target. The interface language is English throughout.

Commit messages: imperative mood, one summary line, a body only when it earns
its place.
